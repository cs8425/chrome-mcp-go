# CDP protocol JSON: refresh, generate, build

The typed CDP client (`internal/cdp/cdp_types_gen.go`, `cdp_methods_gen.go`,
`cdp_events_gen.go`) is **generated** from two vendored schema files and must
never be edited by hand. This doc is the complete workflow for "Chrome changed
the protocol, what do I do".

## 1. Layout

```
internal/cdp/
  protocol/
    browser_protocol.json   # vendored: DOM/Page/Network/... domains
    js_protocol.json        # vendored: Runtime domain (V8/JS)
    README.md               # provenance table (source, date, upstream sha)
    LICENSE                 # Chromium BSD-3-Clause (covers JSON + generated Go)
  gen/main.go               # the generator (reads protocol/, writes *_gen.go)
  client.go                 # hand-written client; carries the //go:generate line
  cdp_types_gen.go          # GENERATED  (types / structs / enums)
  cdp_methods_gen.go        # GENERATED  (one method per CDP command)
  cdp_events_gen.go         # GENERATED  (event types + dispatch)
```

- Generator directive: `//go:generate go run ./gen` in `internal/cdp/client.go`.
  Go runs the command with cwd = `internal/cdp`, which is why the generator reads
  `protocol/browser_protocol.json` etc. by relative path.
- The generator merges the two files' `domains`, sorts them, and rewrites all
  three `*_gen.go` files (each headed `// Code generated by gen (CDP protocol). DO NOT EDIT.`).
- The embedded `version` in the JSON is just `1.3` and does NOT track Chrome.
  The real pin is the provenance table in `protocol/README.md` — keep it current.

## 2. Getting an updated protocol JSON

### (A) GitHub `ChromeDevTools/devtools-protocol` `json/` — primary

This is the source of the currently vendored files, and its layout matches ours
exactly (two separate files).

- Browse: https://github.com/ChromeDevTools/devtools-protocol/tree/master/json
- Raw:
  - https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json
  - https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/js_protocol.json

Overwrite both vendored files, then regenerate:

```sh
# from a checkout of this repo:
curl -fsSL https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json \
  -o internal/cdp/protocol/browser_protocol.json
curl -fsSL https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/js_protocol.json \
  -o internal/cdp/protocol/js_protocol.json
```

`master` moves with each Chrome release. For reproducibility, prefer a **tagged
commit** (the repo tags per Chrome version) and record the exact URL + sha in
`protocol/README.md`.

### (B) npm `devtools-protocol` — alternative (merged single file)

The Puppeteer/DevTools team also publish the schema as a versioned npm package,
regenerated per Chrome release. It ships **one merged `protocol.json`** (all
domains incl. Runtime), so it does not match our two-file layout directly.

```sh
npm pack devtools-protocol@1.3.<build>   # see the package README for Chrome->version
tar -xzf devtools-protocol-*.tgz          # -> package/protocol.json (merged)
```

To feed our two-file loader either (no code change) put the merged file as
`browser_protocol.json` and make `js_protocol.json` an empty
`{"version":{"major":"1","minor":"3"},"domains":[]}`, or teach `loadProtocol`
in `gen/main.go` to also read a single `protocol/protocol.json`.

### (C) Chromium checkout `.pdl` source — authoritative

The single source of truth the JSON is generated from:

```
third_party/blink/public/devtools_protocol/browser_protocol.pdl
third_party/blink/public/devtools_protocol/js_protocol.pdl
content/browser/devtools/protocol/*.pdl    # pulled in by browser_protocol.pdl
```

Compile with Chromium's protocol (pdl -> JSON) toolchain. Only needed when you
must match an exact Chrome build that has no matching upstream tag. Confirm the
current build target name in the checkout — it changes between releases.

## 3. Regenerate

```sh
cd chrome-mcp-go
go generate ./...          # runs `go run ./gen` (cwd internal/cdp)
# -> rewrites internal/cdp/cdp_types_gen.go, cdp_methods_gen.go, cdp_events_gen.go
gofmt -l ./internal/cdp    # gen already formats, but confirm clean (prints nothing)
```

`go generate ./...` from the repo root works too — Go sets the command's cwd to
the package dir holding the directive.

## 4. Build + test

```sh
cd chrome-mcp-go
go build ./... && go test ./... && (cd mcptransport && go test ./...)
```

## 5. After a protocol bump — what usually breaks

The generated API can rename / drop / re-type commands that hand-written
`internal/tools/*.go` calls. `go build` catches it; then:

1. Grep the call sites for the changed method/field, e.g.
   `grep -rn "Page.captureScreenshot\|Network.enable" internal/tools`.
2. Update the tool to the new signature/field.
3. Re-run `go build ./... && go test ./...`.
4. Update the provenance table in `protocol/README.md` (source, sha, date).

## 6. Recommended hygiene

- Treat `internal/cdp/protocol/*` and `cdp_*_gen.go` as a single "vendor +
  regenerate" commit so provenance and output always match.
- Keep build output out of git (`chrome-mcp` binary is already git-ignored;
  confirm with `git status` after building).
- Optional CI job: run `go generate ./...` then `git diff --exit-code` — fails if
  the committed `*_gen.go` is stale relative to the vendored JSON.
- Keep the Chromium `LICENSE` beside the JSON; do not relicense the generated
  code. See `protocol/README.md` → License.
